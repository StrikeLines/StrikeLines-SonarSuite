# SidescanTools Sonar Contact/Target Picker — Implementation Specification

**Document status:** Implementation-ready specification
**Target project:** [sonoware/sidescantools](https://github.com/sonoware/sidescantools)
**Baseline inspected:** upstream `main`, 2026-08-26
**Primary outcome:** Add a SonarWiz-style workflow in which a user clicks a return in the existing Napari waterfall, reviews and names the contact, saves it persistently, and exports the resulting WGS 84 waypoint(s) to GPX.

> This document uses “contact” and “target” synonymously. New code should use `contact` consistently in class, function, table, and field names.

## 1. Executive summary

Extend the existing interactive bottom-detection waterfall instead of creating a second viewer. The existing waterfall is a Napari image layer backed by a three-dimensional array with dimensions:

```text
[chunk, ping-within-chunk, cross-track display sample]
```

The cross-track display row is `PORT | STARBOARD`, with total width `2 * preproc.ping_len`. The existing manual bottom editor already receives mouse events from the sonar and overlay layers. Add a mutually exclusive target-picking mode to this interaction controller. A click in target mode must be converted into:

```text
Napari click (chunk, local ping, display x)
    -> original/global ping index
    -> channel (port or starboard)
    -> normalized near-to-far sample/fraction
    -> source-resolution sample
    -> coordinate from shared georeferencing geometry
    -> persistent SQLite contact
    -> Napari point marker + contact-management row
```

The most important architectural requirement is that contact coordinates and GeoTIFF sample coordinates must be generated by the same geometry implementation. Refactor `Georeferencer.prep_data()` so the navigation smoothing, layback, offsets, channel-side outer-swath calculation, and sample interpolation are reusable. Do not independently reimplement target-position mathematics in the UI.

The contact database must retain the stable acoustic anchor—source file, ping index, channel, and normalized sample/fraction—in addition to the derived latitude and longitude. This permits safe coordinate recomputation after layback or other geometry settings change.

## 2. Goals and scope

### 2.1 Required functionality

The first complete version shall:

1. Add a clearly visible, mutually exclusive **Target Pick** mode to the existing Napari bottom-detection window.
2. Create a contact from a left click on a valid sonar pixel, without modifying the bottom line.
3. Convert the click to an original/global ping index, port/starboard channel, and a normalized near-to-far sample.
4. Compute WGS 84 longitude/latitude through the same navigation, smoothing, layback, offset, and cross-track geometry used for GeoTIFF generation.
5. Store contacts persistently in a project-level SQLite database.
6. Store at least: source file identity/path, global ping index, source ping/packet number, channel, sample, latitude, longitude, timestamp, range, intensity, name, notes, and creation/update metadata.
7. Support an optional image thumbnail centered on the picked return.
8. Show saved contacts as a Napari `Points` layer in the waterfall.
9. Provide a docked contact-management UI for listing, selecting, naming, editing notes, deleting, refreshing coordinates, and exporting contacts.
10. Export selected contacts or all contacts as valid GPX 1.1 waypoints in WGS 84.
11. Detect stale coordinates and allow batch recomputation when layback or other geometry settings change.
12. Preserve current bottom-detection, manual bottom-editing, preprocessing, and GeoTIFF behavior.

### 2.2 Optional follow-on functionality

Design the exporter interface so KML, CSV, and GeoJSON can be added without changing persistence or UI models. These formats are desirable but are not required for the first merge:

- KML placemarks
- CSV rows with all public contact fields
- GeoJSON `Point` features
- Contact sheet/report generation
- Classification/status vocabulary beyond free text

### 2.3 Explicit non-goals

Do not include the following in this modification:

- A new map or mosaic viewer
- Map-to-waterfall navigation or survey-track editing
- Automatic target recognition or classification
- SonarWiz project/database compatibility
- SonarWiz UI, icons, branding, reports, or proprietary code
- A new JSF/XTF decoder
- A new bottom tracker, slant-range correction, EGN algorithm, or towfish dynamics model
- Changes to GeoTIFF rasterization, CRS selection, or output layout except those mechanically required to share geometry code
- Multi-line GeoTIFF mosaicking inside SidescanTools
- Network services or a server database
- Embedding arbitrary binary source files in SQLite

GeoTIFF mosaicking remains downstream. Individual files will be processed using a common EGN table and later combined using a pixelwise maximum-brightness rule over valid pixels:

```text
output(x, y) = max(valid source values covering x, y)
```

NoData must be excluded from that maximum and must not be treated as a real zero/black return. This note is contextual only; no mosaicker is required here.

## 3. Confirmed upstream integration points

The following observations were confirmed against upstream `main`. Recheck them against the exact commit being modified before writing code.

### 3.1 `bottom_detection_napari_ui.py`

File: [`src/sidescantools/bottom_detection_napari_ui.py`](https://github.com/sonoware/sidescantools/blob/main/src/sidescantools/bottom_detection_napari_ui.py)

`run_napari_btm_line()` currently:

- constructs `SidescanFile(filepath)`;
- constructs `SidescanPreprocessor(..., chunk_size, downsampling_factor)`;
- calls `preproc.init_napari_bottom_detect(...)`;
- creates a normal `napari.Viewer`;
- creates the waterfall with:

  ```python
  sidescan_image_layer = viewer.add_image(
      preproc.napari_fullmat,
      name="sidescan image",
      colormap="copper",
  )
  ```

- binds `m` to toggle existing manual bottom annotation;
- defines `custom_mouse_callback(layer, event)` and registers it in `mouse_drag_callbacks` on the sonar, bottom, edge, and binarized layers;
- rounds a three-coordinate `event.position` and interprets it as chunk, ping-within-chunk, and cross-track display sample.

This callback is the interaction hook, but it should be refactored into explicit modes instead of adding an unrelated second callback that could consume the same click.

### 3.2 `sidescan_preproc.py`

File: [`src/sidescantools/sidescan_preproc.py`](https://github.com/sonoware/sidescantools/blob/main/src/sidescantools/sidescan_preproc.py)

`SidescanPreprocessor.init_napari_bottom_detect()` creates:

```text
napari_portside_chunk:   [num_chunk, chunk_size, ping_len]
napari_starboard_chunk:  [num_chunk, chunk_size, ping_len]
napari_fullmat:          [num_chunk, chunk_size, 2 * ping_len]
bottom_map:              [num_chunk, chunk_size, 2 * ping_len]
```

`napari_fullmat` is populated with `np.hstack((portside, starboard))`. The last chunk is zero-padded to `chunk_size`, so a coordinate can be inside the displayed array while not referring to a real ping. Every click path must validate the derived global ping against `sidescan_file.num_ping`.

The waterfall may be downsampled for bottom detection. A contact must therefore retain enough information to map a displayed sample to a full/source-resolution sample without assuming that multiplying by `downsampling_factor` always preserves both endpoints.

### 3.3 `sidescan_file.py`

File: [`src/sidescantools/sidescan_file.py`](https://github.com/sonoware/sidescantools/blob/main/src/sidescantools/sidescan_file.py)

`SidescanFile` exposes the data needed by a contact:

- `data[channel, ping, sample]`
- `ping_len`, `num_ping`, `num_ch`
- `packet_no`
- `timestamp`
- `longitude`, `latitude`
- `sensor_heading`
- `sensor_primary_altitude`, `depth`
- `seconds_per_ping`
- `slant_range`
- `ping_x_axis`

For JSF, `SidescanFile` currently builds the data array using `np.fliplr(data_port)` for channel 0 and unflipped `data_star` for channel 1. This is significant: the array handed to the waterfall is already display-oriented on port. Do not add another JSF-only display flip in contact code.

### 3.4 `georef_thread.py` / `Georeferencer`

File: [`src/sidescantools/georef_thread.py`](https://github.com/sonoware/sidescantools/blob/main/src/sidescantools/georef_thread.py)

`Georeferencer` is currently instantiated for one channel. `prep_data()`:

1. reads per-ping longitude, latitude, heading, slant range, and packet number;
2. removes pings with zero longitude;
3. smooths/interpolates navigation and course over ground;
4. converts navigation to UTM for offset calculations;
5. applies the existing layback calculation and configured X/Y offsets;
6. calculates the outer swath coordinate for the selected channel;
7. builds `swath_width` points from nadir to outer swath with `np.linspace`;
8. flattens those coordinates into `self.nav`.

`channel_stack()` uses raw or processed channel data and flips channel 0 before flattening:

```python
if self.channel == 0:
    ch_stack = np.flip(ch_stack, axis=1)
```

That final flip pairs both channels with the same logical sample convention used by `self.nav`: sample 0 is at/near nadir and the last sample is at the outer edge. Contact code must use this same normalized convention.

Important refactoring constraints:

- `prep_data()` currently filters invalid-navigation pings. A global file ping index is not necessarily equal to a row index in `self.nav` after filtering. The new geometry object must retain an explicit original-ping-to-geometry-row mapping or use arrays aligned to original ping indices with invalid rows marked.
- Existing smoothing windows, spline behavior, ground-range calculation, layback calculation, channel-side formulas, and longitude/latitude interpolation may contain limitations or candidates for future correction. This feature must not silently change them. First refactor mechanically and prove parity. Any georeferencing correction belongs in a separate change with separate reference tests.
- `process()` currently performs its own length checks. Contact geometry must fail clearly for unsupported/too-short files rather than producing a plausible but inconsistent coordinate.

Separate responsibilities as follows:

## 5. Data model and terminology

Use these concepts consistently:

- **Global ping index:** zero-based row in the loaded `SidescanFile`, before navigation filtering.
- **Ping number:** source packet/ping value, normally `sidescan_file.packet_no[global_ping_index]`; not guaranteed to be zero-based or contiguous.
- **Channel:** `0`/`port` or `1`/`starboard`.
- **Display sample:** x-coordinate within one channel of the currently displayed waterfall. Port display order is outer-to-nadir; starboard display order is nadir-to-outer.
- **Normalized sample:** channel-local sample index with a common orientation for both sides: `0 = nadir`, `N - 1 = outer swath`.
- **Sample fraction:** normalized continuous position in `[0.0, 1.0]`, where `0.0 = nadir` and `1.0 = outer swath`. This is the most stable cross-resolution anchor.
- **Source sample:** normalized near-to-far sample index at the full `SidescanFile.ping_len` resolution.
- **Derived coordinate:** WGS 84 longitude/latitude calculated from the acoustic anchor and a specific geometry settings profile.

Recommended core dataclasses:

```python
class Channel(IntEnum):
    PORT = 0
    STARBOARD = 1

@dataclass(frozen=True)
class ContactAnchor:
    source_file_id: int
    global_ping_index: int
    ping_number: int
    channel: Channel
    source_sample_index: int
    sample_fraction: float
    display_chunk: int
    display_ping_index: int
    display_sample_index: int

@dataclass(frozen=True)
class ContactCoordinate:
    longitude: float
    latitude: float
    slant_range_m: float | None
    ground_range_m: float | None
    geometry_profile_id: int
```

## 6. Click conversion and orientation contract

Implement the conversion once as a pure function and use it for picking, marker restoration, thumbnails, and tests.

### 6.1 Global ping

Given rounded/integer Napari data coordinates:

```python
global_ping = chunk_index * preproc.chunk_size + local_ping_index
```

Reject the click if any of the following is true:

- it is outside array bounds;
- `global_ping < 0`;
- `global_ping >= sidescan_file.num_ping` (last-chunk padding);
- the cross-track x-coordinate is outside `[0, 2 * display_channel_width)`;
- the clicked data value is masked/invalid under an established mask;
- navigation/geometry for the ping is unavailable.

Do not create a row and then silently assign `(0, 0)`, NaN, or the uncorrected vessel position.

### 6.2 Port/starboard and normalized display sample

For `display_channel_width = preproc.ping_len` and `display_x` in the concatenated waterfall:

```python
if display_x < display_channel_width:
    channel = Channel.PORT
    channel_display_sample = display_x
    normalized_display_sample = display_channel_width - 1 - display_x
else:
    channel = Channel.STARBOARD
    channel_display_sample = display_x - display_channel_width
    normalized_display_sample = channel_display_sample
```

Then map to a resolution-independent fraction and the full/source-resolution index:

```python
if display_channel_width <= 1:
    raise InvalidContactPixel("channel width must be greater than one")

sample_fraction = normalized_display_sample / (display_channel_width - 1)
source_sample_index = round(sample_fraction * (sidescan_file.ping_len - 1))
source_sample_index = clip(source_sample_index, 0, sidescan_file.ping_len - 1)
```

Use endpoint-preserving fraction conversion rather than blindly multiplying by `downsampling_factor`; decimation and rounding can otherwise shift the outermost sample.

### 6.3 Orientation warning

There must be exactly one UI/display-to-normalized conversion. The UI should not know whether JSF loading or georeferencing internally flips an array. Its contract is only the visible layout:

```text
PORT outer ... PORT nadir | STARBOARD nadir ... STARBOARD outer
```

Before enabling contact creation for a format/subsystem, verify this layout with a synthetic or known file. Add separate JSF and XTF orientation fixtures because upstream comments explicitly note format-related flip differences. A failure here can produce credible-looking but mirrored coordinates and is therefore release-blocking.

## 7. Shared georeferencing refactor

### 7.1 Required public contract

Extract the geometry-building portion of `Georeferencer.prep_data()` into a reusable object or method. One acceptable design is:

```python
@dataclass(frozen=True)
class SwathGeometry:
    channel: int
    sample_count: int
    valid_ping_mask: np.ndarray
    nadir_lon: np.ndarray
    nadir_lat: np.ndarray
    outer_lon: np.ndarray
    outer_lat: np.ndarray
    slant_range_m: np.ndarray
    ground_range_m: np.ndarray
    geometry_settings: "GeometrySettings"

    def coordinate_for_fraction(
        self,
        global_ping_index: int,
        sample_fraction: float,
    ) -> tuple[float, float]: ...

    def coordinate_for_sample(
        self,
        global_ping_index: int,
        sample_index: int,
        sample_count: int | None = None,
    ) -> tuple[float, float]: ...

    def coordinates_for_all_samples(
        self,
        sample_count: int | None = None,
    ) -> np.ndarray: ...
```

`coordinate_for_sample()` converts to a fraction and delegates to `coordinate_for_fraction()`. Both must validate bounds and invalid navigation. `coordinates_for_all_samples()` must use the same interpolation method and ordering, and it becomes the source of `Georeferencer.nav` for existing GeoTIFF generation.

If retaining the current channel-specific `Georeferencer` API is simpler, expose:

```python
georef.prepare_swath_geometry()
georef.coordinate_for_sample(global_ping_index, sample_index, sample_count)
```

The channel may remain `self.channel`; do not duplicate the channel argument in that version. A higher-level contact service can cache one provider per channel.

### 7.2 Geometry settings object

Introduce an immutable, serializable settings object containing every value that can affect a coordinate. At minimum:

```python
@dataclass(frozen=True)
class GeometrySettings:
    vertical_beam_angle: float
    cable_out_m: float
    x_offset_m: float
    y_offset_m: float
    navigation_smoothing_version: str
    geometry_algorithm_version: int
```

Include additional existing options when they affect the computed nav. Serialize with stable key ordering and calculate a SHA-256 settings hash. Avoid hashing incidental UI state or output-only settings such as GeoTIFF compression.

### 7.3 Preserve current behavior first

The initial refactor shall preserve the numerical output of the existing `prep_data()` and `channel_stack()` pairing for both channels. Specifically:

- retain the current invalid-navigation mask semantics;
- retain COG calculation and smoothing;
- retain existing UTM selection and conversion behavior;
- retain current cable-out-to-layback calculation;
- retain X/Y offset formulas;
- retain channel 0 and channel 1 outer-coordinate formulas;
- retain `np.linspace` interpolation from nadir lon/lat to outer lon/lat;
- retain channel 0 backscatter reversal before pairing with near-to-far coordinates.

Create a characterization test from the pre-refactor code before editing it. For a representative fixture, save or compute the old `nav` for both channels, then prove the refactored bulk coordinates are equal within a tight floating tolerance and have the same row ordering. Do not “clean up” suspicious math as part of this feature.

### 7.4 Original-ping alignment

Use arrays aligned to `SidescanFile.num_ping` where possible:

```text
nadir_lon[global_ping_index]
outer_lon[global_ping_index]
valid_ping_mask[global_ping_index]
```

Invalid rows should be NaN plus `False` in the mask. If compact arrays are retained for performance, also retain:

```python
original_to_geometry_row: np.ndarray  # -1 for invalid
geometry_row_to_original: np.ndarray
```

No caller should infer that filtering preserves global indices.

### 7.5 Performance and lifecycle

- Build channel geometry once per opened file and settings hash, then cache it.
- Preparing geometry can be O(number of pings), but a subsequent single contact lookup must be O(1) and must not allocate the full flattened `num_pings * samples` coordinate matrix.
- If preparation is slow, start it when Target Pick mode is enabled, display non-blocking progress, and disable contact creation until ready.
- Cache invalidation must occur when the source file identity, subsystem, channel width, or any geometry setting changes.
- Prefer optional dependency injection of the already-loaded `SidescanFile` into `Georeferencer` to avoid rereading a large JSF twice. Preserve the existing constructor for compatibility.

## 8. Range, intensity, and time derivation

### 8.1 Range

Derive range through the same sample fraction and per-ping metadata used by processing:

- `slant_range_m`: interpolate from nadir to the selected ping/channel's full slant range using `sample_fraction`, or use the canonical existing per-sample axis if one exists and is valid for that ping.
- `ground_range_m`: return the cross-track ground distance represented by the shared geometry for the same fraction. Do not introduce a separate flat-bottom formula in the contact picker if it would differ from current GeoTIFF geometry.

Store null when the underlying value is unavailable. Never substitute zero for unknown range.

### 8.2 Intensity

Store at least one reproducible numeric intensity from the clicked pixel. Recommended fields:

- `intensity_source`: value from the source-resolution `SidescanFile.data` anchor when accessible;
- `intensity_display`: value from `preproc.napari_fullmat` after the waterfall's display preprocessing;
- `intensity_units` or `intensity_pipeline`: short identifier such as `raw`, `db`, `normalized`, or a serialized display-pipeline descriptor.

Do not label a normalized or histogram-equalized display value as raw intensity. The source sample lookup must honor port orientation by using the shared inverse-mapping helper.

### 8.3 Timestamp

Obtain the ping timestamp from `sidescan_file.timestamp[global_ping_index]`. Persist:

- an ISO 8601 text value;
- timezone/UTC status (`utc`, explicit offset, `local-assumed`, or `unknown`);
- optionally the original string/epoch representation if conversion is ambiguous.

GPX `<time>` must only contain a valid UTC/offset timestamp. If source timezone semantics are unknown, either omit `<time>` or require a documented user/project timezone assumption; do not append `Z` to an unverified local time.

## 9. SQLite persistence

### 9.1 Location and connection behavior

Default to a project-level database such as:

```text
<project/work directory>/contacts.sqlite
```

Allow the caller to override the path. Use Python's standard `sqlite3` module, foreign keys, parameterized SQL, explicit transactions, and a nonzero busy timeout. Enable WAL only if it is compatible with the intended storage location; do not assume a network share safely supports it.

All schema changes must use numbered migrations. Never infer a schema solely from the presence of a table.

### 9.2 Required schema

The exact SQL may change during implementation, but it must represent the following model and constraints.

```sql
CREATE TABLE schema_migrations (
    version INTEGER PRIMARY KEY,
    applied_at TEXT NOT NULL
);

CREATE TABLE source_files (
    id INTEGER PRIMARY KEY,
    canonical_path TEXT NOT NULL,
    display_path TEXT NOT NULL,
    file_size_bytes INTEGER,
    mtime_ns INTEGER,
    content_fingerprint TEXT,
    format TEXT NOT NULL,
    subsystem_index INTEGER NOT NULL DEFAULT 0,
    ping_count INTEGER NOT NULL,
    source_sample_count INTEGER NOT NULL,
    created_at TEXT NOT NULL,
    last_seen_at TEXT NOT NULL,
    UNIQUE(canonical_path, subsystem_index)
);

CREATE TABLE geometry_profiles (
    id INTEGER PRIMARY KEY,
    settings_json TEXT NOT NULL,
    settings_hash TEXT NOT NULL UNIQUE,
    algorithm_version INTEGER NOT NULL,

);

CREATE TABLE contacts (
    id INTEGER PRIMARY KEY,
    uuid TEXT NOT NULL UNIQUE,
    source_file_id INTEGER NOT NULL REFERENCES source_files(id),
    geometry_profile_id INTEGER REFERENCES geometry_profiles(id),

    global_ping_index INTEGER NOT NULL CHECK(global_ping_index >= 0),
    ping_number INTEGER,
    channel_index INTEGER NOT NULL CHECK(channel_index IN (0, 1)),
    channel_name TEXT NOT NULL CHECK(channel_name IN ('port', 'starboard')),
    source_sample_index INTEGER NOT NULL CHECK(source_sample_index >= 0),
    sample_fraction REAL NOT NULL CHECK(sample_fraction >= 0.0 AND sample_fraction <= 1.0),

    display_chunk INTEGER,
    display_ping_index INTEGER,
    display_sample_index INTEGER,

    longitude REAL,
    latitude REAL,
    coordinate_status TEXT NOT NULL DEFAULT 'valid'
        CHECK(coordinate_status IN ('valid', 'stale', 'error', 'unavailable')),
    coordinate_error TEXT,

    timestamp_iso TEXT,
    timestamp_basis TEXT,

CREATE INDEX idx_contacts_source_ping
    ON contacts(source_file_id, global_ping_index);
CREATE INDEX idx_contacts_name ON contacts(name);
CREATE INDEX idx_contacts_coordinate_status ON contacts(coordinate_status);

CREATE TABLE contact_thumbnails (
    contact_id INTEGER PRIMARY KEY REFERENCES contacts(id) ON DELETE CASCADE,
    mime_type TEXT NOT NULL DEFAULT 'image/png',
    image_bytes BLOB NOT NULL,
    width_px INTEGER NOT NULL,
    height_px INTEGER NOT NULL,
    ping_radius INTEGER NOT NULL,
    sample_radius INTEGER NOT NULL,
    display_pipeline TEXT,
    created_at TEXT NOT NULL
);

CREATE TABLE contact_coordinate_history (
    id INTEGER PRIMARY KEY,
    contact_id INTEGER NOT NULL REFERENCES contacts(id) ON DELETE CASCADE,
    geometry_profile_id INTEGER REFERENCES geometry_profiles(id),
    longitude REAL,
    latitude REAL,
    coordinate_status TEXT NOT NULL,
    recorded_at TEXT NOT NULL

```

Implementation notes:

- The unique acoustic-anchor constraint prevents accidental duplicate clicks at the exact same pixel. The service may select and focus the existing contact instead of raising an unhandled database error.
- `display_*` fields are convenience/audit values, not the authoritative acoustic anchor. Markers must be reconstructible from global ping, channel, and sample fraction even if the UI chunk size changes.
- Keep WGS 84 coordinates in longitude/latitude regardless of the GeoTIFF output CRS. Validate longitude `[-180, 180]` and latitude `[-90, 90]` in Python before saving/exporting.
- Store thumbnails as optional PNG BLOBs for a portable single-file database. If the project chooses filesystem thumbnails instead, store project-relative paths, use atomic writes, and document relocation behavior.
- `content_fingerprint` may be a full SHA-256 for small files or a documented fast fingerprint (size, mtime, and sampled hash) for large sonar files. Path alone is not sufficient to detect replacement.

### 9.3 Transactions and error behavior

Create a contact and its thumbnail in one transaction. If coordinate calculation fails, the default interactive behavior should not create the contact; show a concise actionable error. An explicit future “save ungeoreferenced contact” option may store `coordinate_status='unavailable'`, but it is not required.

Edits to name/notes must update `updated_at`. Deletion must require an explicit user action and be undoable within the current session if practical; at minimum, ask for confirmation and cascade the thumbnail/history rows.

## 10. Target mode and Napari interaction

### 10.1 Mode controller

Replace the implicit boolean-only interaction with an explicit state:

```python
class InteractionMode(Enum):
    PAN_ZOOM = "pan_zoom"
    BOTTOM_EDIT = "bottom_edit"
    TARGET_PICK = "target_pick"
```

Required behavior:

- Existing `m` shortcut toggles Bottom Edit mode.
- New `t` shortcut toggles Target Pick mode.
- Bottom Edit and Target Pick can never be active simultaneously.
- Entering either edit mode disables layer panning as needed; returning to Pan/Zoom restores it.
- The dock visibly shows the active mode and the cursor changes if Napari permits.
- `Esc` cancels an unsaved draft or returns to Pan/Zoom.
- Target creation occurs once on left-button release with no drag. A drag must never create a trail of contacts.
- A target click must never alter bottom arrays or the bottom overlay.
- Bottom editing must behave exactly as before when Bottom Edit is active.

Prefer registering one interaction dispatcher per relevant layer and routing events by mode. If target picks are restricted to the sonar layer, make markers selectable without allowing the bottom/edge overlay to steal the click.

### 10.2 Contact creation flow

On a valid target click:

1. Convert the event from world to layer data coordinates when layer transforms are present; round only after conversion.
2. Build and validate the `ContactAnchor`.
3. Retrieve or prepare the matching channel geometry.
4. Calculate coordinate, range, time, and intensity.
5. Create a default unique name such as `Target 0001`.
6. Extract the optional thumbnail.
7. Show a draft in the contact dock with editable name and notes.
8. Save on explicit **Save Contact** or Enter. If a low-friction immediate-save workflow is preferred, insert with the default name immediately and make edits autosave; choose one policy and test it consistently.
9. Add the point marker only after the database transaction succeeds.
10. Select the saved row and show its details.

Recommended default: save immediately with a generated name, then focus the name field. This minimizes lost picks while preserving fast field operation.

### 10.3 Points overlay

Create one Napari `Points` layer named `Contacts`. Each point uses coordinates:

```text
[chunk_index, ping_within_chunk, display_x]
```

Reconstruct these values from the authoritative anchor and current UI `chunk_size`/display width:

```python
chunk = global_ping_index // chunk_size
local_ping = global_ping_index % chunk_size

if channel is PORT:
    display_x = (display_width - 1) - round(sample_fraction * (display_width - 1))
else:
    display_x = display_width + round(sample_fraction * (display_width - 1))
```

Use point-layer `features`/properties to associate every marker with contact UUID/ID, name, channel, and status. Do not use the visible point order as the database ID. Distinguish stale/error contacts visually, for example amber/red versus valid cyan or green.

Selecting a marker must select the corresponding contact row. Selecting a row should select the marker; navigating to its chunk is useful but not a release requirement.

## 11. Contact-management dock

Add a docked widget to the existing Napari window. It must remain usable with thousands of contacts and should contain:

- active interaction mode and geometry readiness/status;
- table/list columns: ID/name, source filename, ping number, side, latitude, longitude, status;
- search/filter by name, notes, classification, source, and coordinate status;
- editable name, notes, and optional classification;
- read-only acoustic anchor and derived details;
- thumbnail preview when present;
- actions: New/Pick Mode, Save, Delete, Recompute Selected, Recompute Stale, Export Selected, Export All;
- clear validation and error text.

Use a model/view pattern backed by `ContactStore`, not a separately maintained list of dictionaries. Refresh only affected rows after edits. Long-running geometry preparation, thumbnail batch work, coordinate recomputation, and export must not freeze the UI; use the project's Qt worker/thread conventions and marshal UI updates back to the main thread.

## 12. Thumbnail extraction

Default thumbnail size should be configurable, with an initial recommendation of approximately:

```text
along-track: +/- 100 pings
cross-track: +/- 150 displayed samples
```

Requirements:

- Build a logical 2D waterfall view from valid pings rather than cropping only the current 3D chunk.
- Stitch across chunk boundaries.
- Exclude zero-padded rows beyond `num_ping`.
- Clip cleanly at file start/end and outer image edges.
- Permit the crop to cross the nadir/port-starboard seam if the selected contact is near it.
- Preserve the same display orientation as the main waterfall.
- Normalize/encode deterministically to 8-bit PNG and record the display pipeline used.
- Draw a small crosshair at the exact contact pixel in the user-facing thumbnail. If future quantitative use is expected, optionally retain an unannotated chip separately; do not confuse the crosshair with sonar intensity.
- Extraction failure must not lose an otherwise valid contact. Save the contact without a thumbnail and report a nonfatal warning.

## 13. Coordinate staleness and recomputation

The immutable acoustic anchor is the source of truth. Latitude/longitude is derived state.

### 13.1 Detecting staleness

A contact becomes stale when its saved `geometry_profile.settings_hash` differs from the currently active settings hash, or when the source-file fingerprint/subsystem no longer matches. Settings that affect coordinates include at least cable out, X/Y offsets, vertical beam angle, navigation smoothing/algorithm version, and any future layback choice.

On project/file open:

1. identify the source file;
2. compare its fingerprint and the active geometry hash to each contact;
3. mark mismatches `stale` without overwriting the last coordinate;
4. visually distinguish stale contacts and warn before export.

### 13.2 Recompute operation

For each selected/stale contact:

1. rebuild or retrieve geometry for the active profile;
2. use `global_ping_index`, `channel`, and `sample_fraction` to recalculate coordinate/range;
3. append the old coordinate/profile/status to `contact_coordinate_history`;
4. update derived coordinate/range, profile ID, status, and timestamp in one transaction;
5. retain UUID, name, notes, classification, creation time, acoustic anchor, and thumbnail;
6. refresh marker status and details.

If recomputation fails, retain the previous coordinate, set status to `error`, and store a concise error message. GPX export should default to valid contacts only and show a count of skipped stale/error/unavailable contacts. An explicit “include stale last-known coordinates” option may be added with a warning.

## 14. Export requirements

### 14.1 GPX 1.1 — required

Generate standards-compliant GPX 1.1 XML using a normal XML library so values are escaped correctly. Required structure:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<gpx version="1.1"
     creator="SidescanTools Contact Picker"
     xmlns="http://www.topografix.com/GPX/1/1">
  <wpt lat="29.12345678" lon="-87.12345678">
    <time>2026-08-26T15:20:30Z</time>
    <name>Target 0001</name>
    <desc>Possible wreck debris</desc>
    <type>contact</type>
    <extensions>...</extensions>
  </wpt>
</gpx>
```

Requirements:

- WGS 84 latitude/longitude; no projected coordinates.
- At least 7 decimal places in serialized coordinates, without claiming accuracy the geometry does not provide.
- Stable ordering, preferably source file then global ping then contact ID.
- Default names if the user left a blank/whitespace-only name.
- Notes in `<desc>`.
- `<time>` only when timezone semantics are valid.
- Optional namespace-qualified extensions for UUID, source filename, ping number, channel, sample, range, intensity, and coordinate-profile hash.
- Export selected or all valid contacts.
- Write to a temporary sibling file and atomically replace the destination on success.
- Never overwrite an existing file without the normal file picker/confirmation behavior.
- Validate the resulting XML in tests by reparsing it and asserting namespace/waypoint values.

### 14.2 Optional exporters

Define an interface such as:

```python
class ContactExporter(Protocol):
    suffixes: tuple[str, ...]
    def export(self, contacts: Sequence[Contact], destination: Path) -> None: ...
```

Optional formats should use the same validated query result:

- CSV: UTF-8 with explicit header and ISO timestamps.
- GeoJSON: `FeatureCollection`, WGS 84 `[longitude, latitude]`, contact fields in properties.
- KML: one `Placemark` per contact; coordinates in longitude,latitude order.

## 16. Testing strategy

### 16.1 Unit tests — pixel mapping

Test pure click conversion with small synthetic dimensions:

- first/last port pixel;
- first/last starboard pixel;
- both pixels adjacent to nadir;
- exact channel boundary;
- first and last real ping;
- padded rows in the last chunk;
- negative/out-of-range coordinates;
- odd/even widths where supported;
- downsampled display width versus source width;
- endpoint preservation at fractions 0 and 1;
- marker reconstruction round-trip within at most half a displayed sample;
- duplicate anchor behavior.

Assert the port mapping reverses display x while starboard does not.

### 16.2 Unit/characterization tests — georeferencing

Before refactoring, capture existing bulk `nav` output for representative JSF and XTF fixtures or construct a deterministic fixture around a test `SidescanFile` object. Test:

- both channels;
- straight and curved navigation;
- zero-longitude rows;
- duplicate positions;
- headings crossing 0/360 degrees;
- nonzero cable out and X/Y offsets;
- first/middle/last valid ping;
- near, mid, and outer samples.

Acceptance rule: refactored `coordinates_for_all_samples()` must match legacy `prep_data().nav` ordering and values within an agreed tight tolerance. For every sampled point, `coordinate_for_sample()` must equal the corresponding row in the bulk output.

Also assert that port/starboard coordinates fall on opposite sides of a synthetic survey line and that distance from nadir is monotonic with sample fraction.

### 16.3 Persistence tests

Use temporary SQLite files to test:

- initial migration and reopening;
- future migration from each supported schema version;
- CRUD and field round-trip;
- Unicode names/notes;
- transaction rollback after thumbnail failure/forced SQL failure;
- foreign-key enforcement and thumbnail cascade;
- unique anchor conflict;
- stale-status queries;
- source relinking/fingerprint mismatch;
- coordinate history on recompute.

### 16.4 Export tests

- Parse GPX output as XML and verify the GPX 1.1 namespace.
- Verify latitude/longitude order and precision.
- Verify XML escaping of names and notes.
- Verify timestamp policy for aware, naive/unknown, and absent timestamps.
- Verify stable ordering and selection filtering.
- Verify invalid/stale contacts are skipped with an accurate count.
- If optional exporters are implemented, parse and validate them too.

### 16.5 Thumbnail tests

- center crop;
- every image edge;
- chunk boundary;
- last padded chunk;
- port/starboard seam;
- crosshair position;
- deterministic PNG dimensions/encoding;
- nonfatal failure behavior.

### 16.6 UI/integration tests

Use headless Qt/Napari tests where supported:

- mode mutual exclusion;
- one contact per click release;
- no contact on drag;
- target click does not modify bottom arrays;
- manual bottom edit remains functional;
- marker-to-row and row-to-marker selection;
- database reopen restores markers;
- stale coordinate styling and recompute action;
- long preparation/recompute work does not run on the UI thread.

## 17. Acceptance criteria

The feature is ready when all of the following are demonstrated on at least one representative JSF and, if maintained as supported, one XTF file:

1. Pressing `t` enters Target Pick mode and visibly disables manual bottom editing.
2. Clicking a real return creates exactly one persistent contact; clicking padded last-chunk space creates none.
3. Port and starboard contacts at known pixels map to the correct side and sample with no mirroring.
4. Reopening the same file/project restores contact rows, fields, thumbnails, and markers.
5. Contact coordinates match the coordinate assigned to the same ping/channel/sample by the GeoTIFF navigation array within floating-point tolerance.
6. Changing cable out or X/Y offsets marks existing contacts stale; recomputing changes their coordinates through the shared geometry and preserves their names, notes, anchors, and thumbnails.
7. GPX export opens in at least one independent GPX/GIS reader and contains the same WGS 84 coordinates displayed in the contact UI.
8. Existing bottom detection/edit/save/load behavior passes its previous tests and a manual smoke test.
9. Existing per-channel GeoTIFF generation is numerically unchanged by the geometry refactor, within a documented raster/coordinate tolerance.
10. A prepared geometry returns a single contact coordinate without building the full per-sample navigation matrix.
11. No unhandled exception or partial database row remains after an invalid click, coordinate failure, thumbnail failure, or canceled export.

## 18. Implementation sequence

Implement in this order so the highest-risk orientation and geometry questions are resolved before UI polish:

### Phase 1 — characterize current behavior

### Phase 3 — pure contact domain and persistence

## 20. Required implementation cautions

Treat the following as release blockers, not polish items:

1. **Port orientation:** A duplicated or omitted flip creates mirrored contacts with believable coordinates.
2. **Filtered ping mapping:** `prep_data()` removes invalid-navigation pings; compact geometry indices cannot be treated as global file ping indices.
3. **Downsampling:** A display sample is not automatically a source sample. Persist sample fraction and a source-resolution index.
4. **Geometry divergence:** Contacts may not use simplified bearing/range math separate from GeoTIFF generation.
5. **Settings drift:** Derived coordinates must be traceable to a versioned settings hash and recomputable.
6. **Timestamp ambiguity:** Do not claim UTC when the source parser produced a naive/local datetime.
7. **UI event collisions:** Bottom editing and target picking must be mutually exclusive and deterministic.
8. **Last-chunk padding:** Array bounds alone do not prove a displayed ping is real.
9. **Silent georeferencing changes:** Refactor first; correct or modernize algorithms only in separately tested work.
10. **NoData/mosaicking confusion:** The downstream maximum-brightness mosaic is outside this feature and must not expand the pull request.

## 21. Definition of done

The implementation is done when a user can open a supported sonar file in the existing Napari bottom-detection waterfall, press `t`, click a return, see a persistent labeled marker and thumbnail, edit its name/notes, close and reopen the project without losing it, change layback/settings and explicitly recompute the coordinate, and export valid WGS 84 GPX waypoints—while the contact coordinate is demonstrably identical to SidescanTools' GeoTIFF coordinate for the same ping/channel/sample and all pre-existing bottom-tracking and GeoTIFF behavior remains intact.
